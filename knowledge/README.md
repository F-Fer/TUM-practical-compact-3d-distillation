# Knowledge base: what we tried, what worked, how well

Read this first, before planning or running any experiment. One file per idea in [ideas/](ideas/), sorted by question
rather than by session; the session reports (`results/pba/REPORT*.md` etc.) stay the long-form evidence and are cited
by section. Updated 2026-11-25.

- [evaluation.md](evaluation.md): scene sets, noise levels, timing conventions and evaluation pitfalls. Needed to read
  any number here.
- [runs.csv](runs.csv): one row per scored run on this machine (~950: PBA, track BA, feed-forward, views), generated by
  `scripts/index_runs.py`. Grep it before running a configuration: `grep -i "lm_photo_loss=ncc" knowledge/runs.csv`.
- [infrastructure.md](infrastructure.md): tum2/job/disk lessons.

**Code state:** since 2026-11-10 the photometric / feature-metric BA is one script, `scripts/run_tto_pba.py`, whose
defaults are the current photometric configuration ([pba-method](ideas/pba-method.md)). Options of the alternatives
that are marked rejected or slow here were removed; where an idea file's open points need one of them, its code is at
commit `1c1a921` (`git show 1c1a921:scripts/run_tto_pba.py`, `scripts/pba_analytic.py`). `runs.csv` describes old runs
relative to the current code.

## Workflow

**Before an experiment:** read this page, grep `ideas/` and `runs.csv` for the idea and its options. If it was tried,
the idea file says on which configuration, set and seeds, and whether a later change could alter the answer.

**After an experiment** (also after a negative or inconclusive one):
1. Update the idea file (or create one from the template below): a row in its evidence table with date, setting
   (model, set, seeds, baseline, code path), change, result, source; then update its status line and answer if they
   changed. Mark what it supersedes, don't delete it.
2. Update this README if the current best, a status in the index or the open questions changed.
3. Copy configs + metric JSONs of runs worth keeping to `results/pba/runs/<model>/<run>/` (local, not in git; scratch
   is auto-deleted after 30 days), then `.venv/bin/python scripts/index_runs.py`.
4. Long write-ups still go into a report; the idea files link to it.

Idea file template:

```markdown
# <question or idea>
Status: adopted | rejected | open | partly (<what>) | superseded by <file> · Area: ... · Updated YYYY-MM-DD
**Answer:** one to three sentences, with the key numbers and the set they're on.
## Evidence
| date | setting (model, set, seeds, baseline) | change | result | source (report §, run names) |
## Open / don't repeat
Related: [other](other.md)
```

## Open questions, roughly by value

1. Held-out tests of the current configurations on GIANT and of the VGG configurations with the shared focal.
2. Why NCC helps ETH3D/DTU (the loss or its 4,096 samples) and a stop rule for the NCC LM ([ncc](ideas/ncc.md)).
3. Information for the weak pose directions: a wide-baseline term or tracks on top of B′
   ([pose prior](ideas/pose-prior-and-flat-directions.md), [correspondences](ideas/correspondences-in-pba.md)).
4. DéjàView + TTO ([dejaview-speed](ideas/dejaview-speed.md)): resolution distillation works (336 px +17.7, 420 px
   +3.6 after TTO) but the ARKit-only student loses ETH3D and is slightly worse at 504 px. Outdoor data (R3),
   TTO targets (C1) and a DA3-GIANT teacher (S1, [dejaview-res-distill-scale](ideas/dejaview-res-distill-scale.md))
   didn't help; 4x data / steps did at 336 / 252 px, and diverse cameras (DL3DV + crop / zoom, S0b) fixed DTU and
   lifted every setting by 3-5 after TTO. Open: which part of S0b did it, single setting vs mix with a second seed,
   why better targets on ARKit don't transfer.
5. One vs two radial coefficients in the same configuration on all 11 ETH3D scenes ([radial](ideas/radial-lens-model.md)).
6. Track BA rerun with the shared focal / current polish, so it can be compared fairly ([track-ba](ideas/track-ba.md)).
   Done 2026-11-24 with a GPU pipeline ([fast-sparse-ba](ideas/fast-sparse-ba.md)): dense RoMa tracks + BA reach
   held-out 67.1 from SMALL (NCC-PBA 57.2) at ~36 s; for LARGE B′ (69.9, 0.8 s) equals them. What a no-track method
   must close: ScanNet++ / ETH3D / DTU from small models.
7. Re-tune the per-model priors (`w_prior`, `w_pose`) on the current configurations; GIANT never had any prior.
8. DTU focal drift and the DTU radial coefficient (−0.22) that looks like it absorbs another error.
9. Depth as the bottleneck of the pose ([learned-refinement-step](ideas/learned-refinement-step.md)): GT depth gives SMALL
   + PBA +10.9 AUC@3 on HiRoom/ScanNet++/ETH3D. Which non-oracle depth gets how much of it (larger model's depth with
   SMALL's cameras, monocular depth, a learned depth refiner)? Self-consistent multi-view refinement (alternation) doesn't
   reduce the depth error. Measured since ([depth-bottleneck](ideas/depth-bottleneck.md)): LARGE's depth with SMALL's
   cameras 52.5 vs 43.6 (81 scenes), BASE's 50.7; small refiners and short distillation runs don't transfer; scaling
   the depth distillation is the open experiment for the 5090. 2026-11-24 ([learned-depth-basis](ideas/learned-depth-basis.md)):
   the pose follows the depth's low-frequency error (blur σ = H/16-H/8), and a first-order sensitivity model
   (`lpba_sens.py`, commit 107ea16) predicts the oracles; with the free 8-cell grid the bias comes from the 8-16-cell band.
   Fine-tuning DA3's depth head for PBA (depth / pose-sensitivity / photometric losses, in-domain or ARKit) and learned
   depth bases don't transfer at tum1 scale; test-time augmentation of depth + cameras does help (held-out 43.8 →
   46.7 with 7 passes, [da3-tta](ideas/da3-tta.md)) but costs more than BASE's forward. Scaling the sensitivity loss with a large
   teacher as pseudo-GT is the version for the 5090.

10. **Geometry-guided match refinement** ([guided-match-refinement](ideas/guided-match-refinement.md), 2026-11-25): the
    first learned component on this branch that transfers. It is positive held-out, and the gain saturates in data at
    this refiner size. Open:
    - matched compute (17 s per 100-frame scene on the 3080, 4.2 s cheap; not yet timed on the 5090);
    - all three refiners trained;
    - a wider recurrent refiner, so that B′ isn't needed;
    - the refiner on DA3's own features;
    - predicted precision in the BA;
    - depth from the BA points (a per-frame scale and a 16-cell grid barely help);
    - outdoor / synthetic training data to close the ARKit-only gap (68.1 vs 71.5).
