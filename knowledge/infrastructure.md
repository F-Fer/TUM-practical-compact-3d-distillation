# Infrastructure lessons (tum2, jobs, disks)

Things that cost time once. CLAUDE.md has the setup; this is what went wrong in practice. Updated 2026-11-10.

## Jobs

- **CPU-only jobs see the GPU.** `--gres=gpu:0` jobs still see the node's GPU; set `CUDA_VISIBLE_DEVICES=""` in the
  script (`worker.sh` does it for queues not named `gpu*`). `CUDA_VISIBLE_DEVICES=""` on an `srun` line is ignored:
  SLURM unsets an empty value for a step (REPORT1, REPORT3 §8).
- **Queue race in `$SCRATCH/jobs/pmba/worker.sh`:** two workers on one node popped the same line from a shared queue
  file (NFS stale read after `sed -i` replaced the file), so a scoring line ran twice. Give every worker its own queue
  file (`gpuA.q`, `cpuA.q`, ...), or claim lines with `mkdir` on an append-only queue. (2026-11-09)
- **Job system** (`$SCRATCH/jobs/pmba`, copies in `results/pba/jobs/pmba/`): `snap.sh <tag>` freezes the code into
  `snap/<tag>`; `run.sh <snap> <name> <subset> <score> <overrides>` (MODEL env) runs a configuration on a subset;
  `worker.sh <queue> [idle min]` pops lines; `score_clean.sh <run>` scores recon F1 on 4 sets and then deletes the
  predictions. Job lines are generated by `*_lines.py` files (one per experiment).
- Overlapping steps inside an own job: `srun --jobid=<id> --overlap -n 1` (always `-n 1`); their timings are
  contaminated.
- SLURM's start estimates use the 6 h limits and are far too late. Other groups' jobs may need 56 GB on a node: pin
  short CPU workers to nodes whose running task won't end soon (`sacct -a --name=<job>` gives typical lengths).
- `tail -F` misses NFS-written job logs; poll instead.

## Disks and memory

- **`/scratch/vc17` fills up.** A dev run with predictions is ~2 GB; one night of runs wrote 391 GB and filled the disk
  (2026-11-06), and it was at 100 % again on 2026-11-09 (711 GiB of old PBA predictions deleted). Use `save=false` for
  sweeps, delete `model_results/` after scoring (`score_clean.sh`), keep metrics. Scratch is auto-deleted after 30 days
  untouched: copy the metrics of runs worth keeping to `results/pba/runs/<model>/<run>/` (local, not in git) and
  re-run `scripts/index_runs.py`.
- Antonin's runs in `workspace/tto/` (`ba_fast_it*`, `time_*`, `roma_turbo_q4`, `workspace/ba_iters`, `dvlt*`) are his:
  don't delete them in a cleanup.
- ETH3D recon fusion of the full set needs up to ~58 GB RAM (one fusion worker); the 3 dev scenes ≤ 15 GB. View-subset
  scoring: ≤ 2 fusion workers and 52 GB.
- The login node's `/tmp` (2 GB RAM disk, shared) is often full from other users; Claude Code's temp folder lives
  there. `CLAUDE_CODE_TMPDIR=/scratch/vc17/pr26rb00/claude-tmp` avoids it.
- `/rhome` is a local disk on VC17 mounted elsewhere over NFS: a binary written from the login node fails on VC17 with
  ETXTBSY for ~15 min (CLAUDE.md).

## Git

Run outputs (metric JSONs, configs, per-run comparisons) are not tracked since 2026-11-10; only the knowledge
(`knowledge/`, reports, figures, tables, job scripts). `knowledge/runs.csv` indexes the local run folders. Removing the
tracked copies deletes them from disk in any other clone that merges the change (e.g. `/rhome/pr26rb00/TUM-dvlt`);
restore with `git restore --source=<commit before the merge> --worktree -- results/pba/runs results/pba/runs6`.
